# **7. How do we monitor the application?**

**Interview answer:**

> “I use Amazon CloudWatch to monitor the health and performance of AWS resources and applications. I monitor metrics, collect logs, create alarms, and use dashboards to identify issues such as high CPU, memory pressure, disk usage, high request latency, errors, or unhealthy targets. I use CloudTrail separately to track AWS API activity for auditing.”

### **What is CloudWatch?**

> “CloudWatch is an AWS monitoring and observability service that collects metrics, logs, and events from AWS resources and applications.”

**Flow:** `EC2 / ALB / EKS / RDS → CloudWatch → Metrics + Logs + Alarms`

### **What do you monitor?**

> “Depending on the application, I monitor CPU utilization, memory, disk usage, network traffic, request count, response latency, error rates, ALB target health, and database metrics.”

### **How do you know when something goes wrong?**

> “I configure CloudWatch alarms on important metrics. When a metric crosses the configured threshold, the alarm changes state and can trigger notifications or automation through services such as SNS or Auto Scaling.”

**Flow:** `Metric increases → CloudWatch Alarm → Notification/Action`

### **Example: EC2 CPU is very high**

> “I would check the CloudWatch CPU metric first. If CPU remains high and the Auto Scaling policy is configured for that metric, additional EC2 instances can be launched. I would also investigate the application to determine why CPU usage increased.”

**Flow:** `High CPU → CloudWatch → Alarm/Scaling Policy → ASG → More EC2`

### **What is CloudWatch Logs?**

> “CloudWatch Logs is used to collect and store application and service logs centrally so that we can search them and troubleshoot issues without logging into every server individually.”

### **What is CloudTrail?**

> “CloudTrail records AWS API activity, such as who performed an action, what action was performed, and which AWS resource was affected. It is mainly used for auditing, security investigation, and governance.”

### **CloudWatch vs CloudTrail**

> **CloudWatch → “Is my application or infrastructure working properly?”**

> **CloudTrail → “Who did what in AWS?”**

### **What happens when an application becomes unhealthy?**

> “CloudWatch helps detect the issue through metrics and logs. Depending on the architecture, an alarm can trigger an action such as Auto Scaling, and the operations team can investigate the corresponding logs and metrics.”

### **Production monitoring architecture**

`Users → CloudFront/WAF → ALB → EC2/ECS/EKS → RDS`

`EC2/ECS/EKS/ALB/RDS → CloudWatch → Metrics + Logs + Alarms`

`AWS API activity → CloudTrail → Audit`

### **Most important interview sentence**

> **“I use CloudWatch for monitoring metrics, logs, alarms, and application health, while CloudTrail is used for auditing AWS API activity.”**

The final architecture question is **#8: “What happens when something fails?”** — this connects all the previous topics into **high availability, health checks, failover, self-healing, and troubleshooting.**
## **7. How do we monitor the application?**

**What do we use for AWS monitoring?**: Amazon CloudWatch.

**What is CloudWatch?**: CloudWatch is an AWS monitoring and observability service used to collect metrics, logs, alarms, and application/system monitoring data.

**Why do we use CloudWatch?**: To monitor the health and performance of AWS resources and applications, identify problems, and create alarms when thresholds are exceeded.

**What can we monitor?**: CPU utilization, memory where available, disk usage, network traffic, ALB request/target metrics, RDS metrics, Lambda metrics, application logs, and other service-specific metrics.

**Basic monitoring flow**: EC2/EKS/ALB/RDS → CloudWatch → Metrics/Logs → Alarm → Notification/Action.

---

### **CloudWatch Metrics**

**What are CloudWatch metrics?**: Metrics are numerical measurements that show the performance or health of a resource.

**Example**: EC2 CPU = `90%`, ALB request count increasing, RDS connections increasing.

**Why are metrics useful?**: They help us identify abnormal behavior and decide when to scale or troubleshoot.

---

### **CloudWatch Logs**

**What are CloudWatch Logs?**: CloudWatch Logs stores and helps analyze log data generated by applications and AWS resources.

**Example**: Application errors, Nginx logs, container logs, Lambda logs.

**Why do we use logs?**: To investigate application errors, failures, unusual behavior, and troubleshooting issues.

---

### **CloudWatch Alarm**

**What is a CloudWatch Alarm?**: An alarm monitors a metric against a configured threshold and performs or triggers an action when the condition is met.

**Example**: CPU > `80%` for 5 minutes → CloudWatch Alarm → notification or scaling action.

**Scaling flow**: High CPU → CloudWatch Metric → Alarm/Scaling Policy → More EC2 instances.

---

### **CloudWatch Agent**

**Why do we use the CloudWatch Agent?**: To collect additional operating-system-level metrics and logs from EC2 instances, such as memory and disk usage, that may not be available through basic EC2 monitoring.

**Flow**: EC2 → CloudWatch Agent → CloudWatch Metrics/Logs.

---

### **CloudWatch vs CloudTrail**

**What is the difference?**: CloudWatch is mainly for monitoring performance, metrics, logs, and alarms, while CloudTrail records AWS API activity and helps with auditing who performed which actions.

**Easy memory**: CloudWatch → “Is my application working properly?”, CloudTrail → “Who did what in AWS?”

---

### **How do you troubleshoot using CloudWatch?**

**Answer**: First check the relevant metrics to identify abnormal behavior, then check logs to find the cause, correlate the issue with recent changes or deployments, and take corrective action.

**Troubleshooting flow**: Alarm → Metrics → Logs → Identify root cause → Fix → Verify metrics/logs.

---

### **What happens when CPU suddenly increases?**

**Answer**: I would check CloudWatch CPU metrics, application logs, traffic/request metrics, and recent deployments. If the increase is caused by higher traffic and Auto Scaling is configured, additional capacity can be launched.

**Flow**: Traffic ↑ → CPU ↑ → CloudWatch → Alarm/Scaling Policy → More capacity → Verify recovery.

---

### **What happens when the application suddenly becomes unavailable?**

**Answer**: I would check ALB target health, EC2/EKS health, application logs, CPU/memory, network metrics, security groups, and recent changes to identify where the failure occurred.

**Troubleshooting flow**: User issue → ALB health → Compute health → Application logs → Network → Database → Root cause.

---

### **Do we monitor only EC2?**

**Answer**: No. CloudWatch can monitor many AWS services, including EC2, ALB, RDS, EKS, ECS, Lambda, S3, and others, depending on the metrics and logs available.

---

### **Most important interview memory**

**CloudWatch Metrics**: Performance measurements.

**CloudWatch Logs**: Application/system logs.

**CloudWatch Alarms**: Detect threshold conditions and trigger actions.

**CloudWatch Agent**: Additional OS-level metrics/log collection.

**CloudTrail**: AWS API auditing.

**Main monitoring flow**: **AWS Resources → CloudWatch → Metrics/Logs → Alarm → Action → Verify**.
