# Question 1

**In your DevOps interview, you are asked: A developer wants to change some configuration for debugging purposes for a Pod, but they don't want to impact any other Deployment. What is the safest and most isolated approach?**

## Explanation

The requirement is only for **one developer** to debug the application.

If we modify the existing **ConfigMap** or **Deployment**, every Pod using that ConfigMap may receive the change after a restart. This can affect other developers or even production workloads.

The safest approach is to create a **separate standalone Pod** with the required debug configuration. This keeps the changes isolated and does not affect any existing Deployment.

There are two common approaches:

* Create a temporary Pod using `kubectl run`
* Create a separate Pod YAML with the required environment variables

---

## Method 1: Using `kubectl run`

```bash
# Step 1: Create a standalone debug Pod.
# This Pod is independent of any Deployment.

kubectl run debug-pod \
  --image=myrepo/app:1.0 \
  --env=LOG_LEVEL=debug \
  --restart=Never
```

---

## Method 2: Pod YAML

```yaml
# Step 1: Create a standalone Pod.

apiVersion: v1
kind: Pod

metadata:
  name: debug-pod

spec:

  containers:
    - name: app
      image: myrepo/app:1.0

      # Step 2: Override the logging level
      # only for this Pod.
      env:
        - name: LOG_LEVEL
          value: debug
```

> "If a developer wants to test a configuration change without affecting other Deployments, I don't modify the existing ConfigMap or Deployment because those changes could impact multiple Pods. Instead, I create a separate standalone Pod specifically for debugging. I can either use the **kubectl run** command with the required environment variables or create a separate Pod YAML containing the debug configuration. This isolates the changes to a single Pod and ensures that the existing application remains unaffected."

**Why not modify the existing ConfigMap?**
> "Because multiple Deployments or Pods may be using the same ConfigMap. Updating it could affect all those workloads, especially after they restart."

**Why use `--restart=Never`?**
> "It creates a standalone Pod instead of creating a Deployment or ReplicaSet, which is ideal for temporary debugging."

# Question 2

**In your DevOps interview, you are asked: How would you configure your microservice differently in Development and Production without maintaining two separate Deployment YAML files?**

## Explanation

The application has different configurations for different environments.

For example: Development: LOG_LEVEL=debug, DB_HOST=dev-db and  Production: LOG_LEVEL=error, DB_HOST=prod-db. Instead of maintaining separate Deployment YAML files, we use **Helm templating**.

Helm allows us to keep **one reusable Deployment template** while changing only the values file for each environment.

```yaml
# Development Values File
# values-dev.yaml

environment: dev

logLevel: debug

dbHost: dev-db.company.com

# Production Values File
# values-prod.yaml

environment: prod

logLevel: error

dbHost: prod-db.company.com
```

## Deployment Template

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: backend

spec:

  replicas: 2

  selector:
    matchLabels:
      app: backend

  template:

    metadata:
      labels:
        app: backend

    spec:

      containers:
        - name: backend
          image: myrepo/backend:1.0

          env:

            # Step 1: Read log level from Helm values.
            - name: LOG_LEVEL
              value: "{{ .Values.logLevel }}"

            # Step 2: Read database host from Helm values.
            - name: DB_HOST
              value: "{{ .Values.dbHost }}"
```

```bash
# Deploy to Development
helm install backend ./chart \
-f values-dev.yaml

# Production Values File
helm install backend ./chart \
-f values-prod.yaml
```

> "To avoid maintaining separate Deployment YAML files for different environments, I use **Helm templating**. I keep a single Deployment template and create separate values files such as **values-dev.yaml** and **values-prod.yaml**. These files contain environment-specific configurations like log level, database host, or application URL. Inside the Deployment template, I reference these values using Helm variables such as **{{ .Values.logLevel }}**. During deployment, I specify the appropriate values file, allowing the same Deployment template to be reused for both Development and Production while applying the correct configuration."

**Why is Helm better than maintaining two Deployment YAML files?**
> "Helm reduces duplication, improves maintainability, and ensures consistency because only the configuration changes between environments while the Deployment template remains the same."

**Can Helm values be overridden during deployment?**
> "Yes. In addition to values files, Helm allows overriding values at deployment time using the `--set` option, which is useful in CI/CD pipelines for environment-specific configurations."

# Question

**In your DevOps interview, you are asked: You need to run a database cleanup job every night, but only in the Staging environment and not in Development or Production. How would you implement this in Kubernetes?**

```yaml
# Step 1: Understand the requirement. We need to run a scheduled database cleanup job. The job should execute only in the Staging environment. It should not run in Development or Production.
# Step 2: Create a CronJob resource. A CronJob is used to run scheduled tasks in Kubernetes.
apiVersion: batch/v1
kind: CronJob

metadata:
  name: database-cleanup

  # Step 3: Deploy this resource only in the staging namespace.
  namespace: staging

spec:

  # Step 4: Define when the job should run. This cron expression means: Minute Hour Day Month DayOfWeek 0 2 * * * = Every day at 2:00 AM UTC.
  schedule: "0 2 * * *"

  # Step 5: Define the Job template. Every time the schedule is triggered, Kubernetes creates a Job from this template.
  jobTemplate:

    spec:
      # Step 6: Define the Pod template.
      template:
        spec:
          containers:

            # Step 7: Define the cleanup container.
            - name: cleanup

              # Docker image that performs the cleanup.
              image: myrepo/db-cleanup:1.0

              # Step 8: Pass arguments to the application. Here, the cleanup runs only for staging.
              args:
                - cleanup
                - staging

          # Step 9: Restart the Pod only if the Job fails.
          restartPolicy: OnFailure
```

## Deploy only to the Staging namespace

```bash
# Step 10: Apply the CronJob only in Staging.

kubectl apply -f cronjob.yaml -n staging
```

> "For scheduled tasks in Kubernetes, I use a **CronJob** resource. In this scenario, I create a CronJob that runs the database cleanup every night using the required cron schedule. Inside the **jobTemplate**, I define the Pod that performs the cleanup, including the container image and any required arguments, such as **cleanup staging**. I set the **restartPolicy** to **OnFailure** so the Pod is restarted only if the job fails. To ensure it runs only in the Staging environment, I deploy the CronJob only in the **staging namespace** using `kubectl apply -n staging`. Since the resource exists only in that namespace, it won't run in Development or Production."

**Why use a CronJob instead of a Deployment?**
> "A Deployment is designed for continuously running applications, whereas a CronJob is designed for scheduled tasks that run at specific times."

**What does `restartPolicy: OnFailure` mean?**
> "It means Kubernetes restarts the Pod only if the Job fails. If the Job completes successfully, the Pod exits normally and is not restarted."

**Does Kubernetes automatically restrict a CronJob to one environment?**
> "No. Kubernetes doesn't know about environments by itself. We isolate workloads using namespaces or separate clusters. By creating the CronJob only in the **staging** namespace (or deploying it only to the staging cluster), it runs only in that environment."

**What does the schedule `0 2 * * *` mean?**
> "It follows the standard cron format: `minute hour day-of-month month day-of-week`. So `0 2 * * *` means the job runs every day at **2:00 AM UTC**. If the cluster uses UTC and your team works in IST, you need to account for the time difference or configure the schedule appropriately."

# Question 1

**In your DevOps interview, you are asked: You want to expose specific Pod information, such as the Pod name and Pod IP, as environment variables inside your container. Which Kubernetes feature would you use?**

```yaml
# Step 1: Understand the requirement. The application needs runtime information like the Pod name and Pod IP. These values are created dynamically when the Pod starts, so they cannot be hardcoded or stored in a ConfigMap or Secret.

apiVersion: v1
kind: Pod
metadata:
  name: app-pod

spec:
  containers:
    - name: app
      image: nginx

      # Step 3: Define environment variables. Use fieldRef to read Pod metadata dynamically.
      env:

        # Expose the Pod name.
        - name: POD_NAME
          valueFrom:
            fieldRef:
              fieldPath: metadata.name

        # Expose the Pod IP.
        - name: POD_IP
          valueFrom:
            fieldRef:
              fieldPath: status.podIP
```

> "If my application needs runtime information such as the Pod name or Pod IP, I use Kubernetes' **Downward API** through **fieldRef**. Inside the container's **env** section, I define environment variables and use **valueFrom** with **fieldRef** to reference fields like **metadata.name** for the Pod name and **status.podIP** for the Pod IP. Kubernetes automatically injects these values when the Pod starts, so there's no need to hardcode them or store them in a ConfigMap or Secret."

**Why can't we use a ConfigMap or Secret?**
> "Because the Pod name and Pod IP are generated at runtime and are unique for each Pod. ConfigMaps and Secrets store static configuration, while these values are dynamic."

**What is the Downward API?**
> "The Downward API is a Kubernetes feature that exposes Pod metadata and runtime information, such as the Pod name, namespace, labels, annotations, and Pod IP, to containers through environment variables or mounted files."

# Question 2

**In your DevOps interview, you are asked: Your application must complete a database migration before the main application starts. If the migration fails, the application should never start. How would you implement this in Kubernetes?**

## Complete YAML

```yaml
# Step 1: Understand the requirement. Before the application starts, a database migration must complete successfully. If the migration fails, the application must not start.
apiVersion: v1

# Step 2: Create a Pod.
kind: Pod
metadata:
  name: app-with-migration
spec:

  # Step 3: Define the Init Container. Init Containers always run before the main containers. Kubernetes waits for them to complete successfully.
  initContainers:
    - name: db-migration
      # Image that contains the migration tool.
      image: busybox
      # Replace this command with the actual migration command.
      command:
        - sh
        - -c
        - echo "Running database migration..." && sleep 5

  # Step 4: Define the main application container. This container starts only after all Init Containers complete successfully.
  containers:
    - name: app
      image: nginx
```

> "To ensure the database migration completes before the application starts, I use an **Init Container**. Init Containers always execute before the main application container, and Kubernetes waits for them to finish successfully. I place the database migration command inside the Init Container. If the migration succeeds, Kubernetes starts the main application container. If the migration fails, the Init Container exits with an error, and the main container never starts. This guarantees that the application runs only after the database is in the expected state."

**Why use an Init Container instead of running the migration inside the application?**
> "An Init Container separates initialization tasks from the application, making the startup process cleaner and more reliable. It also ensures the application doesn't start if initialization fails."

**What happens if the Init Container fails?**
> "The main application container is never started. Kubernetes keeps retrying the Init Container according to the Pod's restart policy until it succeeds or the Pod is deleted."

**Can a Pod have multiple Init Containers?**
> "Yes. A Pod can have multiple Init Containers, and Kubernetes runs them sequentially. The next Init Container starts only after the previous one completes successfully. Once all Init Containers finish, the main application containers start."

# Question

**In your DevOps interview, you are asked: Your application logs must be shipped to an external logging system in real time. How would you use a Sidecar container in Kubernetes to achieve this?**

## Complete YAML

```yaml
# Step 1: Create a Pod with two containers. The application container writes logs to a shared volume, and the Sidecar container reads those logs from the same volume and ships them to an external logging system in real time.

apiVersion: v1
kind: Pod

metadata:
  name: app-with-sidecar

spec:

  # Step 2: Create a shared emptyDir volume so both containers can access the same log files.
  volumes:
    - name: shared-logs
      emptyDir: {}

  containers:

    # Step 3: Main application container writes logs into the shared volume.
    - name: application
      image: myrepo/app:1.0

      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/app

      command: ["sh", "-c", "while true; do echo \"$(date) Application is running...\" >> /var/log/app/app.log; sleep 5; done"]

    # Step 4: Sidecar container mounts the same shared volume and continuously tails the log file to forward logs to an external logging system.
    - name: log-shipper
      image: busybox

      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/app

      command: ["sh", "-c", "tail -F /var/log/app/app.log"]
```

> "To ship application logs to an external logging system without modifying the application, I use the **Sidecar container pattern**. Inside the same Pod, I run two containers. The first is the main application container, which writes logs to a shared directory. I create this shared directory using an **emptyDir** volume and mount it into both containers. The second container acts as the Sidecar. It continuously tails the log file from the shared volume and forwards the logs to the external logging platform, such as Fluent Bit, Fluentd, Logstash, or Splunk. This approach keeps the logging functionality separate from the application, making the architecture cleaner and easier to maintain."

**Why use `emptyDir`?**
> "`emptyDir` creates temporary storage that is shared between all containers in the same Pod. It exists for the lifetime of the Pod and is ideal for sharing log files between the application and the Sidecar."

**Why use a Sidecar container instead of adding logging code to the application?**
> "Using a Sidecar separates logging from the application. This keeps the application focused on business logic while the Sidecar handles log collection and forwarding. It also allows us to change the logging mechanism without modifying or rebuilding the application."

**Can the Sidecar send logs directly to Elasticsearch or Splunk?**
> "Yes. In production, the Sidecar typically runs tools such as Fluent Bit, Fluentd, Vector, or Logstash. These tools collect logs from the shared volume and forward them to centralized logging systems like Elasticsearch, Splunk, Grafana Loki, or cloud logging services."

**Why keep both containers in the same Pod?**
> "Containers within the same Pod share the same network namespace and can share storage volumes like `emptyDir`. This makes it easy for the Sidecar to access the application's log files without any additional networking or file-sharing setup."

**Real Production Example**
> "In one of my projects, our applications wrote logs to files inside the container. Instead of changing every application to send logs directly to a logging platform, we used a Sidecar-based approach. The application wrote logs to a shared volume, and the Sidecar collected and forwarded them to the centralized logging stack. This kept the application code unchanged and standardized log collection across all microservices."

**Your e-commerce application has a payment service container that processes payment orders. You need a separate log processor container to parse and send logs to Elasticsearch. Both should run together, share the same volume, and scale as a unit. How would you implement this in Kubernetes?**

## Complete YAML

```yaml
# Step 1: Create a Deployment with two containers in the same Pod. The payment service writes logs to a shared volume, and the log processor (Sidecar) reads those logs and forwards them to Elasticsearch. Since both containers are in the same Pod, they scale together.

apiVersion: apps/v1
kind: Deployment

metadata:
  name: payment-with-logger

spec:
  replicas: 3

  selector:
    matchLabels:
      app: payment-with-logger

  template:
    metadata:
      labels:
        app: payment-with-logger

    spec:

      # Step 2: Create a shared emptyDir volume so both containers can access the same log files.
      volumes:
        - name: shared-logs
          emptyDir: {}

      containers:

        # Step 3: Main payment service container writes logs to the shared volume.
        - name: payment-service
          image: myrepo/payment-service:1.0

          ports:
            - containerPort: 8080

          volumeMounts:
            - name: shared-logs
              mountPath: /var/log/payment

        # Step 4: Sidecar log processor reads logs from the shared volume and forwards them to Elasticsearch.
        - name: log-processor
          image: myrepo/log-processor:1.0

          env:
            - name: ELASTICSEARCH_URL

          volumeMounts:
            - name: shared-logs
              mountPath: /var/log/payment
```

# Question 2

**Your microservice needs to communicate with multiple external APIs such as Payment API and Shipping API. Each API requires different authentication and rate limiting. How would you implement this using the Ambassador pattern in Kubernetes?**

## Complete YAML

```yaml
# Step 1: Create a Deployment with two containers. The main application communicates only with localhost, while the Ambassador container handles all outbound API calls, authentication, and rate limiting.

metadata:
  name: app-with-ambassador

  replicas: 2

  selector:
    matchLabels:
      app: app-with-ambassador

  template:
    metadata:
      labels:
        app: app-with-ambassador

    spec:

      containers:

        # Step 2: Main application container communicates only with the Ambassador container using localhost.
        - name: application
          image: myrepo/app:1.0

            - name: API_ENDPOINT

        - name: ambassador
          image: myrepo/api-proxy:1.0

          ports:
            - containerPort: 9000

          env:
            - name: PAYMENT_API
              value: "https://payment-api.company.com"

              value: "https://shipping-api.company.com"

This keeps the application code simple because it doesn't need to manage authentication, routing, or external API policies."

> "It separates external communication logic from the application. Authentication, retries, rate limiting, routing, and API-specific configurations are handled by the Ambassador instead of the application."

So, while both run as additional containers in the same Pod, their responsibilities are different.

# Question 1

**Your company runs a machine learning pipeline with a Data Preprocessing Pod and a Model Training Pod. For better performance, you want the Model Training Pod to run on the same node or, if that's not possible, in the same availability zone as the Data Preprocessing Pod. How would you configure this in Kubernetes?**

## Complete YAML

```yaml
# Step 1: Create a Deployment for the training application and use Pod Affinity. The scheduler first tries to place the training Pod on the same node as the preprocessing Pod. If that's not possible, it prefers the same availability zone to reduce network latency.

apiVersion: apps/v1
kind: Deployment

metadata:
  name: model-training

spec:
  replicas: 1

  selector:
    matchLabels:
      app: model-training

  template:
    metadata:
      labels:
        app: model-training

    spec:

      # Step 2: Configure Pod Affinity rules.
      affinity:
        podAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:

            # First preference: Same worker node.
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: role
                      operator: In
                      values:
                        - preprocess
                topologyKey: kubernetes.io/hostname

            # Second preference: Same Availability Zone.
            - weight: 50
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: role
                      operator: In
                      values:
                        - preprocess
                topologyKey: topology.kubernetes.io/zone

      containers:
        - name: training
          image: myrepo/model-training:1.0
```

> "To reduce data transfer latency, I use **Pod Affinity**. In the Deployment YAML, I configure **preferredDuringSchedulingIgnoredDuringExecution**. My first preference is to schedule the training Pod on the same worker node as the preprocessing Pod using the topology key **kubernetes.io/hostname** with a weight of **100**. If scheduling on the same node isn't possible, I add another affinity rule with a weight of **50** using the topology key **topology.kubernetes.io/zone**, so Kubernetes tries to place both Pods in the same availability zone. This improves performance while still allowing scheduling flexibility."

**Why use `preferredDuringSchedulingIgnoredDuringExecution` instead of `requiredDuringSchedulingIgnoredDuringExecution`?**
> "I use **preferred** because it's a soft rule. Kubernetes tries to satisfy the affinity, but if it cannot, the Pod is still scheduled elsewhere. If I use **required**, the Pod remains in the Pending state until the condition is satisfied."

**Why is the node affinity weight higher than the zone affinity weight?**
> "Scheduling on the same node provides the lowest latency because communication happens locally. If that's not possible, scheduling within the same availability zone still reduces network latency compared to cross-zone communication."

# Question 2

**You are deploying a critical web frontend application with multiple replicas. For high availability, you don't want multiple replicas to run on the same node or in the same availability zone. How would you configure this?**

## Complete YAML

```yaml
# Step 1: Create a Deployment with multiple replicas and configure Pod Anti-Affinity. This ensures replicas are distributed across different worker nodes and availability zones, reducing the impact of node or zone failures.

apiVersion: apps/v1
kind: Deployment

metadata:
  name: web-frontend

spec:
  replicas: 3

  selector:
    matchLabels:
      app: web-frontend

  template:
    metadata:
      labels:
        app: web-frontend

    spec:

      # Step 2: Configure Pod Anti-Affinity.
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:

            # Prefer different worker nodes.
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - web-frontend
                topologyKey: kubernetes.io/hostname

            # Prefer different availability zones.
            - weight: 50
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - web-frontend
                topologyKey: topology.kubernetes.io/zone

      containers:
        - name: web
          image: nginx
          ports:
            - containerPort: 80
```

> "To improve high availability, I use **Pod Anti-Affinity**. I configure **preferredDuringSchedulingIgnoredDuringExecution** so Kubernetes avoids placing multiple frontend replicas on the same worker node. I use the topology key **kubernetes.io/hostname** with a higher weight to spread Pods across different nodes. I also add another anti-affinity rule using **topology.kubernetes.io/zone**, so if possible, replicas are distributed across different availability zones. This minimizes the risk of a single node or zone failure affecting multiple replicas of the application."

**What is the difference between Pod Affinity and Pod Anti-Affinity?**
> **Pod Affinity** brings related Pods closer together to improve communication and reduce latency.
> **Pod Anti-Affinity** spreads similar Pods across different nodes or zones to improve high availability and fault tolerance.

**When would you use `requiredDuringSchedulingIgnoredDuringExecution`?**
> "I use **required** when the scheduling rule is mandatory. For example, if two replicas must never run on the same node due to compliance or strict high availability requirements. If the rule cannot be satisfied, Kubernetes keeps the Pod in the Pending state."

**"What's the difference between Node Affinity, Pod Affinity, and Pod Anti-Affinity?"**
* **Node Affinity** → Schedules Pods based on **node labels** (for example, SSD nodes, GPU nodes, or specific instance types).
* **Pod Affinity** → Schedules Pods **close to other Pods** with matching labels to improve communication.
* **Pod Anti-Affinity** → Schedules Pods **away from other Pods** with matching labels to improve availability and resilience.
