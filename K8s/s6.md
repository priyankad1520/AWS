# **Question 55: How would you distribute application replicas evenly across multiple Availability Zones in Kubernetes?**

## **Requirements**

* Application replicas should be evenly distributed across different Availability Zones.
* A single Availability Zone failure should not affect all application replicas.
* If the distribution rule cannot be satisfied, the Pod should not be scheduled.

---

## **Explanation**

> "In our project, the Kubernetes cluster spanned multiple Availability Zones. To improve fault tolerance, I used **Topology Spread Constraints**. First, I labeled all application Pods with **app=web** so Kubernetes could identify Pods belonging to the same application. Then I configured the topology key as **topology.kubernetes.io/zone**, which tells Kubernetes to spread Pods across different Availability Zones. I set **maxSkew** to **1**, ensuring that the difference in the number of replicas between any two zones is not more than one. Finally, I set **whenUnsatisfiable** to **DoNotSchedule**, so Kubernetes would leave the Pod in the Pending state instead of violating the distribution rule."

---

## **Pod Label**

```yaml
metadata:
  labels:
    app: web
```

**Purpose:** Identify Pods that belong to the same application.

---

## **Topology Spread Constraint**

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: web
```

**Purpose:** Evenly distribute application Pods across Availability Zones.

---

## **Container**

```yaml
containers:
- name: web-app
  image: nginx:latest
```

**Purpose:** Deploy the web application.

**Purpose:** Prevent automatic Pod updates after template changes.

### ✅ Interview Tip

For DaemonSet updates, remember these two strategies:

| Strategy          | Behavior                                | Use Case                                             |
| ----------------- | --------------------------------------- | ---------------------------------------------------- |
| **RollingUpdate** | Automatically updates Pods gradually    | Normal production updates                            |
| **OnDelete**      | Updates Pods only after manual deletion | Critical infrastructure, networking, security agents |

This comparison is worth memorizing because it's a common follow-up interview question after discussing DaemonSets.
