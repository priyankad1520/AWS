# **How would you manage Spring Boot configuration without rebuilding the Docker image every time?**

> "In our project, we stored application configuration in a **ConfigMap** instead of embedding it inside the Docker image. The ConfigMap contained the `application.properties` file, which we mounted into the container under the `/config` directory. Spring Boot automatically loads configuration from this location during startup. Whenever configuration changes, we update the ConfigMap and restart the pods, allowing the application to use the new settings without rebuilding the image."

---

## ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: spring-config

data:
  application.properties: |
    logging.level.root=INFO
    feature.enabled=true
```

**Purpose:** Store non-sensitive runtime configuration.

---

## Deployment

```yaml
volumeMounts:
- name: config-volume
  mountPath: /config

volumes:
- name: config-volume
  configMap:
    name: spring-config
```

**Purpose:** Mount the ConfigMap into the container.

---

## Apply Configuration

```bash
kubectl apply -f configmap.yaml
```

```bash
kubectl rollout restart deployment spring-app
```

---

# **Why do we use a ConfigMap?**

> "ConfigMaps separate configuration from the application image, allowing configuration changes without rebuilding or republishing the container."

# **How do you manage different configurations for Dev, QA, and Production while using the same Docker image?**

> "In our project, we built the Docker image only once and reused it across all environments. Environment-specific values such as log level and database hostname were stored in separate ConfigMaps, while sensitive values like passwords were stored in Secrets. During deployment, Kubernetes injected the correct ConfigMap and Secret based on the target namespace or Helm values, allowing the same image to run in Development, QA, and Production."

The statement **"define a default backend inside the Ingress"** depends on the Ingress controller.

If different subdomains (`app.domain.com`, `admin.domain.com`) need different services, you need **multiple host rules**, not a single wildcard rule.

# **How do you configure path-based routing using a single Ingress?**

> "In our project, we used a single Ingress resource with path-based routing. Requests starting with **/api** were forwarded to the API service, while requests to **/ui** were routed to the frontend service. The path type was configured as **Prefix** so that nested paths were also matched. For unmatched requests, we configured a default backend to return a custom 404 response."

---

## Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: app-ingress

spec:
  rules:
  - http:
      paths:

      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80

      - path: /ui
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80

  defaultBackend:
    service:
      name: custom-404
      port:
        number: 80
```

### Correction: Rewrite Target

If you're using the **NGINX Ingress Controller**, the rewrite annotation works together with **regular expression capture groups**.

Instead of saying:

> "`rewrite-target: /v1/$2` rewrites `/api/users` to `/v1/users`"

show the matching path as:

```yaml
path: /api(/|$)(.*)
```

and enable regex:

```yaml
nginx.ingress.kubernetes.io/use-regex: "true"
```

Then:

* `/api/users` → `/v1/users`
* `/api/orders/10` → `/v1/orders/10`

Without regex, `$2` won't exist.

# **How do you rewrite request URLs in Kubernetes Ingress without modifying the application?**

> "In our project, external clients accessed APIs using the `/api` path, but the legacy application expected requests under `/v1`. Since we couldn't modify the application, we configured URL rewriting in the Ingress using NGINX rewrite annotations. The Ingress rewrote incoming requests before forwarding them to the backend service, allowing external and internal URL structures to remain different."

---

## Rewrite Annotation

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /v1/$2
```

**Purpose:** Rewrite the request before forwarding it to the backend.

---

## Path Rule

```yaml
spec:
  rules:
  - http:
      paths:
      - path: /api(/|$)(.*)
        pathType: ImplementationSpecific

        backend:
          service:
            name: legacy-service

            port:
              number: 80
```

# **How do you configure rate limiting in Kubernetes Ingress?**

> "In our project, we configured rate limiting at the Ingress layer using NGINX annotations. This ensured excessive requests were blocked before reaching the backend application, protecting the service without requiring any application changes."

---

## Rate Limiting

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/limit-rps: "10"
    nginx.ingress.kubernetes.io/limit-burst-multiplier: "5"
```

**Purpose:** Limit each client to **10 requests per second** while allowing short traffic bursts.

---

## Backend

```yaml
backend:
  service:
    name: api-service

    port:
      number: 80
```

# **Why do we apply rate limiting at the Ingress?**

> "Applying rate limiting at the Ingress prevents excessive traffic from reaching the application, reducing resource consumption and protecting backend services from abuse."

---

> "The Ingress Controller rejects the excess requests, typically returning an HTTP **429 Too Many Requests** response, while the backend application remains protected."
