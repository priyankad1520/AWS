# # **How do you deploy a new version with zero downtime while ensuring an instant rollback if something goes wrong?**

> "In our project, we used Kubernetes **Rolling Update** strategy for zero-downtime deployments. Inside the Deployment YAML, I configured **maxUnavailable: 0** and **maxSurge: 1**, so Kubernetes creates a new pod before terminating an old one. I also configured a **readiness probe**, so traffic is sent only after the new pod becomes healthy. To avoid terminating in-flight requests, I used **terminationGracePeriodSeconds** along with a **preStop hook**, allowing the old pod to shut down gracefully. I also configured a **Pod Disruption Budget** to ensure a minimum number of pods always remained available during maintenance. Finally, I set **revisionHistoryLimit**, so if anything failed, I could quickly roll back using **kubectl rollout undo**, and Kubernetes automatically restored the previous ReplicaSet."

There are two important corrections before you use these notes in an interview.

### 1. Image updates using `latest`

The statement **"Kubernetes detects that the image has changed and automatically begins a rolling update"** is **not correct**.

Kubernetes **does not automatically redeploy** a Deployment just because a new image is pushed to the registry, even if:

```yaml
image: my-app:latest
imagePullPolicy: Always
```

`imagePullPolicy: Always` only means **when a pod is created or restarted**, Kubernetes always pulls the latest image. Existing pods are **not restarted automatically**.

In real projects, the CI/CD pipeline usually does one of these:

* Updates the image tag (recommended, e.g., `2.0`, `2.1`, Git SHA)
* Executes:

  ```bash
  kubectl rollout restart deployment my-app
  ```
* Or runs:

  ```bash
  kubectl set image deployment/my-app app=my-app:2.0
  ```
* Or updates the Helm values and performs `helm upgrade`.
* If using Argo CD, Git is updated and Argo CD performs the rollout.

For a **5+ years DevOps interview**, avoid recommending `latest` for production because interviewers often ask about it.

A better interview answer is:

> "In production, we avoid using the `latest` tag. Our CI pipeline builds a uniquely versioned image, updates the Deployment (or Helm values), and Kubernetes performs a rolling update. We keep `revisionHistoryLimit` configured so we can quickly roll back using `kubectl rollout undo`."
